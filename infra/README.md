# Optional batch-analysis deployment

This directory contains an optional way to package, validate, and run the football analysis
workflow as a finite batch job. It is separate from the hackathon's required submission path.
Reviewers do not need AWS, Kubernetes, or Argo CD to regenerate and validate `Mojarra Labs.csv`;
the required Windows commands are in `Mojarra Labs.md`.

## Why these components fit this workload

The analysis processes a complete match and writes result files, so it behaves like a batch job,
not an always-on web service. The optional deployment pieces address those operational needs:

- **Docker** packages the Python dependencies and project code so the evaluation runs in a
  consistent environment. Licensed match data is excluded from the build context and must be
  provided locally at runtime.
- **GitHub Actions** builds and runs the evaluation image and checks Terraform formatting,
  Terraform configuration, and Kubernetes manifest schemas before changes are merged.
- **Kubernetes Job** runs the evaluation to completion with a deadline and retry policy; a
  persistent volume keeps the CSV/JSON evaluation reports after the Pod exits.
- **Argo CD** synchronizes the Kubernetes manifests from the public Git repository, making the
  desired local deployment visible and repeatable from version-controlled configuration.
- **Terraform** defines a private, encrypted, versioned S3 bucket as a possible artifact-storage
  target for a future AWS deployment.

## Current scope and status

- Kubernetes and Argo CD were run locally with `kind`; this is not an EKS deployment.
- The current Kubernetes Job runs `evaluation/run_evaluation.py` and stores its evaluation reports.
  It does **not** generate the `Mojarra Labs.csv` possession submission.
- The submission CSV is generated by `starter/baseline.py` using the command in the main README.
- Terraform was initialized, formatted, validated, and planned. `terraform apply` was not run, so
  the S3 bucket was **not created** in AWS.
- No licensed match data, generated full-match submission CSV, or evaluation reports belong in
  this public repository.

## Local prerequisites

The optional deployment path requires Docker Desktop in Linux-container mode. Running the
Kubernetes example additionally requires `kubectl`, `kind`, and a local cluster. Terraform commands
in this directory validate the configuration without provisioning cloud resources. None of these
tools is required for the official CSV generation and validation workflow. The Mojarra Labs run
uses the pinned dependencies in `requirements-mojarra.txt`; `requirements.txt` remains the original
competition environment file.

## Run the batch commands with Docker

From the repository root in Windows PowerShell, build the image. The `.dockerignore` excludes the
licensed `data/` directory, so the build context contains code and dependencies only:

```powershell
docker build -t mtah-evaluation:local .
```

The image's default command runs the public-baseline evaluator, as in CI:

```powershell
docker run --rm mtah-evaluation:local
```

To generate the team's CSV in the container, mount the authorized data directory read-only and a
separate output directory writable. Replace no source files and do not copy the data into the image:

```powershell
$repoRoot = (Get-Location).Path
$outputDir = Join-Path (Split-Path -Parent $repoRoot) "mojarra-docker-output"
New-Item -ItemType Directory -Force $outputDir | Out-Null
docker run --rm `
  --mount "type=bind,source=$repoRoot\data,target=/app/data,readonly" `
  --mount "type=bind,source=$outputDir,target=/output" `
  mtah-evaluation:local python starter/baseline.py --window 50 `
  --output "/output/Mojarra Labs.csv"
```

The output is `Mojarra Labs.csv` in the sibling `mojarra-docker-output` directory. Validate it with
the host Python environment using the command in `Mojarra Labs.md`. The local generator and the
default evaluator were both verified with this image; the generated labels matched the checked-in
`baseline_smooth50.csv` reference.
